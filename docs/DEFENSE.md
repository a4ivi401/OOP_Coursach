## 2. Застосунок за 30 секунд

Консольний інтернет-магазин електроніки з двома ролями. **Покупець** переглядає каталог із фільтрами за ціною,
брендом і категорією, кладе товари в кошик та оформлює замовлення з купоном на знижку. **Адміністратор**
керує товарами, складом, купонами й статусами замовлень і дивиться звіти. Рішення складається з трьох
проєктів: бізнес-логіка в DLL, консольний інтерфейс і тести. Дані зберігаються в JSON через серіалізацію.
Виконано всі вимоги, зокрема з позначками *, ** і ***.

## 3. Детальний опис застосунку

### 3.1. Архітектура

```
ElectroShop.UI  ──(ProjectReference)──►  ElectroShop.Core.dll  ◄──  ElectroShop.Tests
  екрани, введення, Spectre.Console        моделі, сервіси, винятки,     71 тест xUnit
                                           репозиторії, JSON
```

- **UI нічого не знає про те, як зберігаються дані й рахуються знижки.** Він працює лише через фасад `Shop`.
- **Core нічого не знає про консоль.** Тому ту саму DLL можна підключити до WPF чи веб-застосунку, а тести працюють без UI.
- Залежність одна: UI → Core. Зворотного зв'язку немає; ядро повідомляє UI про події через `event LowStock`.

### 3.2. Предметна область

| Сутність | Що зберігає | Особливості |
|---|---|---|
| `Category` | назва, опис | унікальна назва; не видаляється, якщо містить товари → `EntityInUseException` |
| `Product` | артикул, назва, бренд, категорія, ціна, залишок, гарантія, опис, характеристики | артикул `ABC-123` (регулярний вираз), «мало на складі» при ≤ 3 шт. |
| `Customer` | ПІБ, email, телефон, адреса, сума покупок, кошик | телефон `0931112233` → `+380931112233`; рівень лояльності обчислюється з суми покупок |
| `Cart`, `CartItem` | товари в кошику | ≤ 20 шт. одного товару; кошик зберігається у файлі між запусками |
| `Order`, `OrderItem` | номер, клієнт, позиції, ціни, доставка, купон, статус, історія | позиція — **знімок** назви й ціни, тож зміна ціни в каталозі не змінює старі замовлення |
| `Coupon` (abstract) | код, термін дії, мін. сума, ліміт використань, активність | 3 нащадки з різним розрахунком знижки |

### 3.3. Бізнес-правила (варто знати напам'ять)

| Правило | Значення |
|---|---|
| Відсотковий купон | 1–50 % на все замовлення |
| Фіксований купон | 1–50 000 ₴, але не більше вартості товарів |
| Купон на категорію | 1–70 % лише на товари однієї категорії; без таких товарів у кошику — помилка |
| Перевірки купона | активний → вже діє → не прострочений → ліміт не вичерпано → сума ≥ мінімальної → (для категорійного) є товари категорії |
| Лояльність | Бронзовий 0 % · Срібний від 20 000 ₴ — 3 % · Золотий від 50 000 ₴ — 5 % · Платиновий від 100 000 ₴ — 7 % |
| Обмеження знижок | купон + лояльність разом ≤ 50 % вартості товарів |
| Доставка | самовивіз 0 ₴ · пошта 80 ₴ · кур'єр 150 ₴ · **безкоштовно від 5 000 ₴** після знижок |
| Статуси | Нове → Оплачено → Відправлено → Доставлено; скасувати можна лише Нове чи Оплачено |
| Скасування | товар повертається на склад, використання купона відкочується, сума покупок клієнта зменшується |
| Адмін | PIN `1234`, у коді лише SHA-256 хеш; після 3 помилок панель блокується до перезапуску |

### 3.4. Порядок оформлення замовлення (`OrderService.PlaceOrder`)

1. Зібрати позиції з кошика → якщо порожньо, `EmptyCartException`.
2. Перевірити наявність **кожного** товару → `OutOfStockException`.
3. Перевірити купон → `InvalidDiscountException`.
4. Розрахувати ціну (`PriceCalculator`).
5. **Лише після всіх перевірок** списати товар зі складу, згенерувати подію `LowStock`, зарахувати використання
   купона, збільшити суму покупок клієнта, створити замовлення і очистити кошик.

Завдяки цьому порядку замовлення або оформлюється повністю, або дані взагалі не змінюються. Це
перевіряє тест `PlaceOrder_WithInvalidCoupon_ChangesNothing`.

### 3.5. Інтерфейс

- **Головне меню**: вхід покупця, реєстрація, адмін-панель, «Про програму», «Зберегти та вийти».
- **Покупець**: картки з рівнем лояльності та кошиком; каталог з фільтрами; картка товару; кошик; покрокове
  оформлення (кошик → доставка → купон → підсумок → підтвердження); мої замовлення (деталі, скасування);
  акції; профіль із прогрес-баром до наступного рівня.
- **Адміністратор**: KPI-дашборд і сповіщення про товари, що закінчуються; CRUD товарів, категорій, купонів;
  поповнення складу та характеристики; зміна статусів замовлень; клієнти, відсортовані за сумою покупок;
  звіти з гістограмою виручки за категоріями, діаграмою статусів, топ-5 товарів.

### 3.6. Валідація введення: два рівні

1. **Модель** (`Core`): кожен setter перевіряє значення і кидає `ArgumentException` або власний виняток.
2. **UI**: `Input.Ask(label, parse)` передає введений рядок у функцію `parse`, яка зазвичай викликає setter моделі.
   Якщо він кинув виняток, під полем з'являється червоне повідомлення і запит повторюється.

Правило записано лише один раз, у моделі, а UI його повторно використовує. Тому неможлива ситуація,
коли UI пропустив значення, а модель його відхилила, або навпаки.

### 3.7. Збереження

- При старті: файл є → завантажити; файлу немає → демо-дані.
- При виході, при Ctrl+C і за командою адміністратора дані зберігаються.
- Запис іде у `shop.json.tmp`, потім файл атомарно замінюється, тож збій під час запису не псує дані.
- Якщо у файлі синтаксична помилка або некоректне значення (від'ємна ціна), виникає `DataStorageException`;
  програма пропонує зробити резервну копію `.bak` і продовжити.

| Патерн | Де |

## 7. Ймовірні запитання та відповіді

### Про ООП загалом

**— Назвіть чотири принципи ООП і покажіть їх у коді.**
Інкапсуляція: приватні поля й властивості з валідацією (`Product.Price`). Успадкування: `EntityBase` → моделі,
`Coupon` → 3 купони. Поліморфізм: `CalculateRawDiscount` перевизначено в кожному купоні. Абстракція:
абстрактні класи `Coupon`, `EntityBase`, `MenuScreen` та інтерфейси.

**— Чим абстрактний клас відрізняється від інтерфейсу?**
Абстрактний клас може мати стан (поля) і реалізацію спільних методів, а клас успадковує лише один такий клас.
Інтерфейс — це контракт без стану, і клас може реалізувати кілька інтерфейсів. Тому `Coupon` — абстрактний
клас (спільні поля й перевірки), а `IDiscountPolicy` — інтерфейс (купон і `LoyaltyDiscountPolicy` не мають
спільного предка).

**— Що таке `virtual`, `abstract`, `override`?**
`abstract` — методу немає реалізації, нащадок **зобов'язаний** її надати (`CalculateRawDiscount`). `virtual` — реалізація
за замовчуванням, нащадок **може** її перевизначити (`ValidateSpecific` порожній у базовому класі,
`CategoryCoupon` перевизначає). `override` — саме перевизначення.

**— Де статичний та динамічний поліморфізм?**
Динамічний: виклик `coupon.CalculateDiscount()` через посилання базового типу. Статичний (перевантаження):
два конструктори `ShopException`, перевантажені `AddCancelResult` з бібліотеки, generic-методи `Input.Ask<T>`.

**— Чому немає публічних полів?**
Це вимога завдання й принцип інкапсуляції: поле не може перевірити значення, а властивість може. Навіть
константи оформлено як статичні властивості.

### Про колекції та generics

**— Навіщо `Repository<T>`, якщо є `List<T>`?**
Репозиторій ховає список і дає доменні операції: пошук за `Id` з винятком `EntityNotFoundException`, захист
від дублікатів, індексатор. Обмеження `where T : class, IEntity` гарантує наявність `Id`. Один клас обслуговує
п'ять типів сутностей.

**— Що означає `where T : class, IEntity`?**
Обмеження узагальненого параметра: `T` має бути посилальним типом і реалізовувати `IEntity`, тому в коді
репозиторію можна звертатися до `item.Id`.

**— Чому назовні `IReadOnlyList`, а не `List`?**
Щоб зовнішній код не міг додати чи видалити елемент в обхід бізнес-правил, наприклад додати в кошик товар без
перевірки залишку.

**— Де `IComparable`, а де `IComparer`?**
`IComparable<Product>` — природний порядок товару (за назвою), реалізований у самому класі. `IComparer<Product>` —
зовнішні стратегії сортування (`ProductPriceComparer` тощо); їх вибирає фабрика `ProductComparers.For(option)` і
передає в `List.Sort`.

### Про винятки

**— Навіщо власні винятки, якщо є `InvalidOperationException`?**
Вони несуть доменні дані (`OutOfStockException.Available`, `InvalidDiscountException.CouponCode`) і дозволяють
перехоплювати саме бізнес-помилки за базовим типом `ShopException`, не ковтаючи системні збої.

**— Де ловляться винятки?**
Централізовано в `Ui.Run(action)`: кожен пункт меню виконується через нього. Під час введення помилки
перехоплюються у валідаторі `Input.Ask` і показуються під полем. `DataStorageException` обробляється в `App.LoadData`.
Неочікувані системні винятки не ловляться, щоб не приховати реальну помилку.

**— Чому валідація в моделях кидає `ArgumentException`, а не власний виняток?**
Це стандартна семантика .NET для некоректного аргументу (як у прикладі з методички). Власні винятки
використано для **бізнес-ситуацій**: брак товару, неправильний купон, недозволений статус. Виняток —
межі відсотка купона: там одразу `InvalidDiscountException`, бо це вимога варіанта.

**— Що буде, якщо купон недійсний посеред оформлення?**
Нічого не зміниться: усі перевірки (`BuildItems`, `ResolveCoupon`) виконуються до списання товару. Це перевіряє тест
`PlaceOrder_WithInvalidCoupon_ChangesNothing`.

### Про серіалізацію

**— Як серіалізується абстрактний `Coupon`?**
Атрибути `[JsonPolymorphic]` і `[JsonDerivedType]` додають у JSON поле `"$type"`, за яким десеріалізатор створює
потрібний клас-нащадок. Перевіряє тест `Coupons_KeepTheirConcreteTypes`.

**— Як серіалізуються приватні колекції?**
Через `[JsonInclude]` на приватній властивості (`Cart.ItemsData`), а публічна `IReadOnlyList` позначена `[JsonIgnore]`.
Інкапсуляція не порушується.

**— Що буде, якщо файл зіпсувати вручну?**
Синтаксична помилка JSON або значення, яке не пройшло валідацію setter-а, перетворюється на `DataStorageException`.
Програма покаже причину й запропонує створити `.bak` та почати з демо-даних або з порожнього магазину.

**— Чому один файл, а не по файлу на сутність?**
Дані пов'язані між собою (замовлення посилаються на клієнтів і товари). Один знімок `ShopSnapshot` зберігає їх
узгодженими й записується атомарно.

### Про бізнес-логіку

**— Як рахується знижка?**
`PriceCalculator.Calculate`: сума позицій → знижка купона (поліморфно) → знижка лояльності за рівнем → обмеження
сумарної знижки 50 % → доставка (безкоштовна від 5 000 ₴ після знижок) → разом.

**— Чому в замовленні зберігаються назва й ціна товару?**
Це знімок на момент покупки. Якщо адміністратор змінить ціну або видалить товар, історія замовлень і звіти
залишаться коректними.

**— Як працює подія `LowStock`?**
`OrderService` оголошує `event EventHandler<LowStockEventArgs>`. Після списання товару, якщо його ≤ 3 шт., подія
генерується. `App` підписує на неї `NotificationCenter.OnLowStock`, а адмін-панель показує сповіщення. Ядро
нічого не знає про інтерфейс.

**— Навіщо `TimeProvider`?**
Щоб у тестах і генераторі демо-даних підставляти «фіктивний» час, наприклад перевірити прострочений купон без
очікування. Це стандартний абстрактний клас .NET 8+.

**— Як захищено PIN?**
У коді лише SHA-256 хеш, порівняння через `CryptographicOperations.FixedTimeEquals`, після трьох помилок
вхід блокується. Для навчального проєкту цього достатньо; у реальній системі була б автентифікація
користувачів із сіллю та зберіганням поза кодом.

### Про інтерфейс

**— Чому Spectre.Console?**
Це популярна бібліотека для консольних застосунків на .NET. Вона дає таблиці, меню зі стрілками й діаграми,
тож UI-код стає коротким і зосереджується на логіці, а не на ручному малюванні рамок.

**— Як організовано екрани?**
Абстрактний `MenuScreen` реалізує цикл: заголовок → `RenderBody()` → меню з `GetMenu()` → виконання через `Ui.Run`.
Нащадок визначає лише вміст і пункти — це шаблонний метод. Таких екранів 12.

**— Як влаштована валідація введення?**
`Input.Ask<T>(label, parse)` використовує `TextPrompt` з валідатором, що викликає `parse`. Зазвичай `parse` —
це setter моделі, тому правило записано лише один раз, у бізнес-бібліотеці.

### Про тести

**— Що тестуєте?**
Валідацію моделей, усі причини `InvalidDiscountException`, розрахунок цін і лояльності, оформлення та скасування
замовлень, подію `LowStock`, фільтри й компаратори, збереження та відновлення з файлу, обробку пошкодженого файлу.
Разом 71 тест.
